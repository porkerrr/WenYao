# 专业六爻排盘缺口解决方案

> 状态：已确定执行路线，规则内容尚待验证
>
> 适用范围：问爻 Android MVP 至专业排盘正式发布
>
> 制定日期：2026-09-13

基于公开实现候选进一步细化的来源准入、规则文档、穷举测试、历法适配和阶段计划，见 [`EXPERIMENTAL_PROFESSIONAL_CHART_PLAN.md`](EXPERIMENTAL_PROFESSIONAL_CHART_PLAN.md)。

## 1. 结论

采用分阶段组合方案：

```text
专业引擎接口与验证状态
        ↓
公开、可追溯的实验规则集
        ↓
多来源差分验证
        ↓
领域专家黄金案例验收
        ↓
正式规则集
```

与此同时，产品范围分成两条发布轨道：

- 基础 MVP：三硬币起卦、六十四卦、本卦、动爻、变卦、本地历史和 AI 解释，可以继续交付。
- 专业排盘：八宫、纳甲、五行、六亲、六神、世应、月建、日辰和旬空，在专家验收前只能标记为“未开放”或“实验性”，不能声称专业正确。

这个方案允许工程继续推进，但不会把代码自洽、参考实现一致或测试通过误写成术数规则已经得到权威确认。

## 2. 事实、推理与风险

### 2.1 事实

- 当前 Android MVP 已完成基础卦象、历史和可配置 AI 服务。
- 技术方案要求专业排盘规则可追溯、版本化，并通过不少于 20 个领域专家黄金案例。
- 当前没有经产品负责人和领域顾问批准的 `RULESET.md`，也没有专家黄金案例。
- 月建、日辰、旬空涉及时区、换日、节气边界等口径；部分规则存在流派差异。
- 开源许可证允许使用代码，不等于其输出自动成为权威规则。

### 2.2 推理

- 完全停工会浪费等待时间；直接补齐九类专业字段又无法证明正确。
- 先建立接口、版本和验证状态，可以把“能计算”和“已验证”分开。
- 实验规则集可以用于开发、差分和收集案例，但不能自动升级为正式规则集。
- 最终的正式发布门仍必须由独立专家案例决定。

### 2.3 主要风险

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 隐式选择流派 | 同一输入在不同口径下结果不同 | 所有决定写入规则文档，未决定项写 `TBD` |
| 参考实现共同出错 | 多个程序一致但仍然错误 | 引入传统规则来源和专家黄金案例 |
| 实验结果被当成正式结果 | 用户被误导 | UI、数据库和 API 都携带验证状态 |
| 算法升级改写旧记录 | 历史结果失去可追溯性 | 历史保存完整快照及规则版本 |
| 许可证不兼容 | 无法闭源分发或产生披露义务 | 只复制许可证明确且兼容的代码；未知、GPL、AGPL 仅作人工研究 |
| 历法边界错误 | 节气或子时附近排盘错误 | 固定时区、换日和节气数据源，加入边界案例 |

## 3. 产品发布策略

### 3.1 四种验证状态

```kotlin
enum class VerificationStatus {
    NOT_AVAILABLE,
    EXPERIMENTAL,
    CROSS_VALIDATED,
    VERIFIED
}
```

含义：

- `NOT_AVAILABLE`：没有可展示的专业排盘；正式 MVP 默认使用此状态。
- `EXPERIMENTAL`：规则可重复且有来源，但尚未通过专家验收；只用于内部测试或明确标注的 Beta。
- `CROSS_VALIDATED`：指定能力与冻结的外部工程实现完成穷举差分；它证明实现一致，不等于传统口径或领域正确性已获确认。
- `VERIFIED`：规则文档已批准，专家黄金案例全部通过，才可用于正式专业排盘。

任何代码路径都不得根据“测试通过”“两个参考实现一致”或版本号达到 `1.0` 自动设置 `VERIFIED`。

### 3.2 用户可见文案

| 状态 | 允许文案 | 禁止文案 |
|---|---|---|
| `NOT_AVAILABLE` | 专业排盘正在验证中 | 精准专业排盘 |
| `EXPERIMENTAL` | 实验性排盘 · Ruleset 0.x · 未经专家验收 | 标准六爻、权威结果 |
| `CROSS_VALIDATED` | 静态排盘已通过工程交叉验证 · 尚未完成专家验收 | 权威排盘、专家认证 |
| `VERIFIED` | 专业排盘 · Ruleset 1.x | 预测必然发生、绝对准确 |

无论状态如何，结果都必须保留“传统文化研究与娱乐参考”及高风险场景提醒。

## 4. 技术架构

### 4.1 专业引擎边界

```kotlin
interface ProfessionalChartEngine {
    fun calculate(input: ProfessionalChartInput): ProfessionalChartResult
}

data class ProfessionalChartResult(
    val rulesetId: String,
    val rulesetVersion: String,
    val verificationStatus: VerificationStatus,
    val chart: ProfessionalChart?
)
```

约束：

- `NOT_AVAILABLE` 时 `chart` 必须为 `null`。
- `EXPERIMENTAL`、`CROSS_VALIDATED` 和 `VERIFIED` 必须携带非空 `rulesetId`、`rulesetVersion` 和完整快照。
- UI 不计算任何专业规则。
- AI 只能解释引擎输出，不能补算或静默修正缺失字段。
- 历史记录保存当次规则集、验证状态和专业盘快照；算法升级不重算旧记录。

### 4.2 规则集草案

建立 `docs/RULESET-DRAFT.md`，每项必须记录：

1. `ruleset_id` 与版本。
2. 参考来源、版本、页码或稳定链接。
3. 已确认决定、负责人、确认日期。
4. 未解决决定及其影响；统一写 `TBD`。
5. 八宫及游魂、归魂规则。
6. 纳甲表、内外卦和阴阳顺逆规则。
7. 五行及六亲映射。
8. 世应定位规则。
9. 六神按日干起法。
10. 月建按节气月或农历月。
11. 日辰、旬空算法。
12. 默认时区、换日点、晚子时处理。
13. 节气时刻数据源和边界策略。
14. 闰年、夏令时、设备时钟异常策略。

仍为 `TBD` 的规则不得进入正式构建的计算路径。

### 4.3 差分验证框架

```text
固定输入
  ├─ WenYao Experimental Engine
  ├─ Reference Adapter A
  ├─ Reference Adapter B
  └─ Calendar Reference
             ↓
       逐字段差分报告
```

差分结果分为：

- `CONSENSUS`：所有实现一致。
- `EXPECTED_DIVERGENCE`：差异符合已记录的流派决定。
- `UNEXPLAINED_DIVERGENCE`：未解释差异，阻止升级规则版本。

参考引擎只在测试环境使用，不进入生产 APK。差分一致只能证明实现间一致，不能替代专家验收。

## 5. 分阶段执行计划

### 阶段 A：验证状态和接口骨架

预计：2–4 人日。

任务：

1. 新增 `ProfessionalChartEngine`、输入输出模型和 `VerificationStatus`。
2. 提供正式构建使用的 `UnavailableProfessionalChartEngine`。
3. Room 增加规则集 ID、版本、验证状态和可空快照，并编写 migration test。
4. 结果页根据状态显示关闭、实验或已验证文案。
5. 测试未验证状态无法显示为 `VERIFIED`，且不会生成虚构字段。

退出条件：正式 APK 中专业排盘保持 `NOT_AVAILABLE`，接口和数据迁移测试通过。

### 阶段 B：实验规则集 0.1

预计：6–13 人日，包括来源整理。

任务：

1. 完成 `RULESET-DRAFT.md`，所有规则有来源或明确 `TBD`。
2. 对无争议、已记录来源的规则独立实现，不复制许可证不兼容代码。
3. 实现八宫、纳甲、五行、六亲、世应和六神。
4. 历法模块单独实现或采用固定版本、宽松许可证的成熟库。
5. 规则集标记为 `EXPERIMENTAL`，只在 internal/debug 构建启用。

退出条件：规则文档无隐式决定，64 卦静态规则测试和全部领域不变量通过。

### 阶段 C：多来源差分验证

预计：7–15 人日。

任务：

1. 选择至少两个独立、许可证明确的参考来源或实现。
2. 建立只用于测试的适配器，不把不兼容依赖打入 APK。
3. 生成不少于 1000 个确定性案例，覆盖全部六十四卦和动爻组合抽样。
4. 增加节气前后、23:00/00:00、跨时区、夏令时和闰年边界。
5. 产出机器可读差分报告；每个差异必须得到解释或修复。

退出条件：`UNEXPLAINED_DIVERGENCE = 0`；实验状态不变。

### 阶段 D：专家验收和正式发布

预计：取决于顾问可用性；工程处理约 3–7 人日。

任务：

1. 领域顾问审阅并签署 `RULESET.md`。
2. 获取不少于 20 个专家独立排盘案例，建议目标为 50–100 个。
3. 黄金案例覆盖九类专业字段和所有历法边界。
4. 所有差异形成规则决议记录，不通过“修改测试答案”掩盖差异。
5. 专家案例 100% 通过后发布新的规则版本，并人工批准升级为 `VERIFIED`。

退出条件：技术方案第 12.4 节发布门禁全部满足。

## 6. 来源与许可证治理

参考资料进入开发前登记：

| 字段 | 要求 |
|---|---|
| 名称和 URL | 可追溯到具体仓库、文献或供应方 |
| 版本 | 固定 commit、release 或文献版本 |
| 许可证 | 保存许可证文本和版权归属 |
| 使用方式 | 规则来源、人工研究、黑盒对比或代码依赖 |
| 可复制范围 | 明确是否允许复制代码、表格或测试数据 |

处理原则：

- 传统文献或公开规则说明用于形成规格，代码独立实现。
- MIT、BSD、Apache 等宽松许可代码只有在确有必要时使用，并保留要求的声明。
- GPL、AGPL、无许可证或许可证不清晰的项目不复制代码、表格或大段数据，也不作为生产依赖。
- 商业 API/SDK 必须确认商业使用、缓存、展示、服务终止和数据处理权利。

## 7. 验收矩阵

| 层级 | 主要证据 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 单元/属性测试 | 规则函数、穷举和不变量 | 代码按已写规则运行 | 规则本身符合某一流派 |
| 差分测试 | 多来源逐字段报告 | 能发现大量工程偏差 | 多数实现一致即权威正确 |
| 专家黄金案例 | 独立案例与签署规则 | 符合已确认规则集 | 结果能确定预测未来 |
| 模拟器/真机 | 页面、历史、恢复和无障碍 | App 交互可用 | 专业规则正确 |
| AI 评测 | Schema、证据引用和安全用语 | AI 没有明显越界或重算 | AI 解释具有确定性 |

专业规则升级为 `VERIFIED` 必须同时满足：

```text
RULESET.md 已批准
AND 专家黄金案例 >= 20
AND 黄金案例 100% 通过
AND UNEXPLAINED_DIVERGENCE = 0
AND 所有自动化测试、Lint、构建Debug 和 Release 构建通过
AND 关键流程通过至少两个 Android API 级别验收
```

## 8. 决策与成本

推荐方案不是最短路径，而是当前约束下风险与进度最平衡的路径。

| 选择 | 近期成本 | 能否立即发布基础 MVP | 能否立即声称专业正确 |
|---|---:|---|---|
| 只等待专家 | 0.5–2 人日 | 可以 | 不可以 |
| 实验规则集 | 6–13 人日 | 可以 | 不可以 |
| 正式缩减 MVP | 1–2 人日 | 可以 | 不涉及 |
| 差分验证 | 7–15 人日 | 可以 | 不可以 |
| 接口与状态骨架 | 2–4 人日 | 可以 | 不涉及 |
| 商业顾问/SDK | 3–10 人日加采购周期 | 可以 | 取决于验收合同 |

如果目标是尽快验证产品，应先交付基础 MVP，并依次执行阶段 A、B、C；同时寻找领域顾问。若已有明确商业发布日期，则优先采购“规则文档 + 机器可读表 + 黄金案例”的顾问交付，而不是长期依赖不可审计的远程排盘 API。

## 9. 最小下一步

无需等待顾问即可执行：

1. 按实验性专业排盘方案建立 `docs/ruleset/RULESET.md`、`TESTPLAN.md` 和 `SOURCE_REGISTRY.md`，所有未确认决定保持 `TBD`。
2. 实现 `ProfessionalChartEngine` 接口和 `VerificationStatus`。
3. 为 Room 增加规则版本与验证状态快照，提供迁移测试。
4. 正式构建固定使用 `UnavailableProfessionalChartEngine`。
5. UI 只显示“专业排盘正在验证中”，不显示空表或虚构字段。
6. 产品负责人确认是否正式把专业排盘调整到 MVP v1.1。

只有第 6 项是产品范围决策；前五项可以直接进入开发。
