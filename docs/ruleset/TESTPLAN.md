# 专业排盘测试计划

> 对象：`wenyao-mainstream-experimental:0.2.0-draft`
>
> 原则：测试证明实现符合已写规则；专家验收才证明规则集符合选定口径。

## 1. 测试层次

| 层级 | 目的 | 是否可单独支持 `VERIFIED` |
|---|---|---|
| 规格完整性测试 | 阻止来源、口径或 `TBD` 被静默遗漏 | 否 |
| 单元与穷举测试 | 验证每条机械规则 | 否 |
| 属性测试 | 验证跨输入不变量 | 否 |
| 历法边界测试 | 验证时区、节气和换日行为 | 否 |
| 多引擎差分 | 定位实现分歧 | 否 |
| 完整黄金案例 | 由领域专家验证选定规则口径 | 是，且须满足全部门禁 |
| Android 验收 | 验证展示、持久化、恢复与无障碍 | 否 |

当前静态核心的工程交叉验证冻结为：参考实现 `yaomancy/liuyao-engine@53291663a4c733c4cbdfa174a8d3075475c07fd3`，64 卦 × 10 日干共 640 行规范化结果，SHA-256 为 `141f099beae1537bb0611ef4e12a7a3044979bb61430421a0261db916e66985a`。该结果只支持 `STATIC_CORE` 的 `CROSS_VALIDATED`，不能单独升级为 `VERIFIED`。

## 2. 规格完整性测试

- `SRC-001`：所有规则引用的 `S-*` 编号存在于 `SOURCE_REGISTRY.md`。
- `SRC-002`：生产依赖来源必须有固定 commit/release、许可证和使用范围。
- `RULE-001`：`VERIFIED` 构建的规则文件不得包含 `TBD`。
- `RULE-002`：每条 `R-*` 规则至少被一个 `T-*` 测试覆盖。
- `RULE-003`：规则版本变化必须伴随迁移或历史快照兼容测试。

## 3. 静态规则穷举

### T-PALACE-001：64 卦宫属与世应

- 输入：64 个阴阳六爻组合，不含动静差异。
- 断言：每卦唯一宫、唯一卦类、唯一世、唯一应。
- 断言：世应只出现一四、二五、三上三组配对。
- 断言：宫五行与八纯卦五行一致。
- 预期数据必须由规则推导后经传统来源复核，不直接复制未准入仓库数据。

### T-NAJIA-001：48 个单卦槽位

- 输入：8 单卦 × 内外卦 × 3 爻。
- 断言：天干、地支和顺逆完全符合 `R-NAJIA-001` 的最终表。

### T-NAJIA-002：384 个完整爻位

- 输入：64 卦 × 6 爻。
- 断言：上下卦分别纳甲，组合卦宫不能覆盖单卦纳甲结果。
- 断言：每一爻五行与地支映射一致。

### T-LIUSHEN-001：60 个六神位置

- 输入：10 日干 × 6 爻。
- 断言：初爻起神正确，向上顺序循环且六神不重复。

### T-LIUQIN-001：25 个生克关系

- 输入：5 本宫五行 × 5 爻五行。
- 断言：同我、生我、我生、克我、我克唯一映射到对应六亲。

### T-XUNKONG-001：60 甲子

- 输入：完整六十甲子。
- 断言：每个输入输出两个不同地支；同旬十个干支结果一致；六旬合计覆盖预期组合。
- 预期表必须独立登记来源，不能调用 S-003 生成预期值再测试 S-003。

## 4. 属性与组合测试

- `T-PROP-001`：同一输入、规则版本和历法约定重复运行，序列化快照逐字节稳定。
- `T-PROP-002`：只改变动静值但不改变本卦阴阳时，宫、世应和本卦纳甲不变。
- `T-PROP-003`：翻转一个动爻时，变卦恰有对应一爻阴阳变化。
- `T-PROP-004`：AI 响应不能覆盖或新增任何确定性盘面字段。
- `T-PROP-005`：规则升级后读取旧历史，仍显示原 `rulesetVersion` 和原快照。

## 5. 历法边界测试

每个用例保存 UTC 时间、`ZoneId`、offset、节气时刻来源和期望口径：

- 每个“节”交接前 1 秒、交接时刻、后 1 秒。
- 22:59:59、23:00:00、23:59:59、00:00:00、00:00:01。
- 同一 `Instant` 在 `Asia/Shanghai`、`UTC` 和至少一个存在 DST 的时区。
- DST 跳时和重复时段；不存在或歧义本地时间必须显式解析。
- 2 月 29 日、年末年初、立春前后。
- `getDayInGanZhiExact` 与 `getDayInGanZhiExact2` 差异点作为决策案例，不能默认为任一 API。
- 同一 `Instant` 在不同用户时区的月建必须一致；节气必须先按 UTC+8 转为绝对时刻，禁止直接使用任意用户时区钟表值。
- 以香港天文台 2026 年历书的分钟级时刻作为独立粗粒度 oracle，覆盖小寒、立春、立夏、立秋和大雪；允许不同天文算法存在最多一分钟舍入差，但不得出现小时级时区偏移。秒级 inclusive 边界另由锁定 provider 一致性测试覆盖。
- 专业引擎、历法或快照失败时，基础卦与独立生成状态仍必须成功保存。

## 6. 差分验证

开发工具对同一规范化输入输出逐字段报告：

```text
caseId | field | WenYao | Reference-A | Reference-B | status | ruleId | note
```

状态仅允许：

- `CONSENSUS`：实现输出一致，仍不代表权威正确。
- `EXPECTED_DIVERGENCE`：差异符合已记录的规则决议。
- `UNEXPLAINED_DIVERGENCE`：差异未解释，阻止发布。

禁止多数投票产生测试预期。差异必须由 `RULESET.md`、可追溯传统来源或领域顾问裁决。

最低差分集：64 个静卦、每卦六个单动组合、六神十日干、旬空六十甲子和全部历法边界案例。

## 7. 完整黄金案例

每个案例必须由项目实现之外的领域顾问独立给出：

- 原始问题（可匿名）、六爻、起卦时间、时区和历法口径。
- 本卦、变卦、宫、卦类、世应。
- 六爻纳甲、五行、六亲、六神和动静。
- 月建、日辰、旬空。
- 专家姓名/标识、规则流派、确认日期和来源证明。

发布门槛：专家黄金案例 >= 20，目标 50；全部字段 100% 通过。任何争议必须产生规则决议，禁止只修改测试答案。

## 8. Android 与数据验收

- `NOT_AVAILABLE` 不展示空盘或伪造字段。
- `EXPERIMENTAL` 在结果页、历史详情和分享/导出中均显示未完成专家校验。
- `VERIFIED` 只能由人工批准的规则配置产生。
- Room migration 保留现有历史，并保存新盘面的完整快照、时区、规则版本和验证状态。
- 飞行模式、进程重启、旋转和应用升级后结果一致。
- 至少两个 Android API 级别完成起卦、结果、历史、删除和恢复验证。

## 9. CI 发布门禁

实验构建要求：规格完整性、全部已实现规则测试、Android 单测、Lint、Debug 构建通过，且 `UNEXPLAINED_DIVERGENCE = 0`。

正式构建还要求：

```text
RULESET.md 无 TBD 且已签署
AND 专家黄金案例 >= 20
AND 黄金案例 100% 通过
AND Release 构建通过
AND 两个 Android API 级别验收通过
AND 产品负责人完成人工升级审批
```
