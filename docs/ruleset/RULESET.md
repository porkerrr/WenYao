## 1. 输入与编码

- 六爻从下到上编码为索引 `0..5`，显示名为初、二、三、四、五、上。
- 唯一二进制表示约定：`bit0=初爻`、`bit1=二爻`、…、`bit5=上爻`；因此 `lower=key & 0b111`，`upper=(key shr 3) & 0b111`。专业规则核心只接收 `HexagramPattern(lower, upper)`，裸位串仅允许在输入边界转换。
- 单爻值沿用现有引擎：`6=老阴`、`7=少阳`、`8=少阴`、`9=老阳`。
- 本卦阴阳：`6/8=阴`，`7/9=阳`。
- 动爻：`6/9`；变卦只翻转动爻阴阳。
- 专业排盘输入必须携带起卦 `Instant` 和显式 `ZoneId`；适配器使用固定 `CalendarConvention`，日柱按用户当地零点换日，月柱按固定 `UTC+08:00`（不读取 IANA 历史规则）的 lunar-java 节气交接时刻换月。

现有基础卦象规则已由 `LiuyaoEngineTest` 覆盖；专业规则不得改变基础起卦结果。

## 2. 八宫、卦类与世应（R-PALACE-001）

候选基线来自 S-001，并用 S-002 差分验证：

| 卦类 | 变化路径 | 世爻 | 应爻 |
|---|---|---:|---:|
| 八纯/本宫 | 本宫卦 | 上（6） | 三（3） |
| 一世 | 初爻变 | 初（1） | 四（4） |
| 二世 | 初、二爻变 | 二（2） | 五（5） |
| 三世 | 初、二、三爻变 | 三（3） | 上（6） |
| 四世 | 初至四爻变 | 四（4） | 初（1） |
| 五世 | 初至五爻变 | 五（5） | 二（2） |
| 游魂 | 五世基础上第四爻复原 | 四（4） | 初（1） |
| 归魂 | 游魂基础上下卦三爻复原 | 三（3） | 上（6） |

约束：

- 64 卦宫属、卦类、世应已冻结为纯数据测试夹具 `palace_golden.csv`，并包含乾为天、天风姤、天地否、地天泰等方向锚点。夹具用于防止实现与测试循环证明；传统文献与领域专家复核仍未完成。

## 3. 纳甲（R-NAJIA-001）

采用京房八宫纳甲候选口径：上下卦分别装纳甲，不按整卦所属宫直接给六爻配支。

- 阳卦：乾、坎、艮、震；地支按候选规则顺行。
- 阴卦：坤、巽、离、兑；地支按候选规则逆行。
- 每个单卦分别定义内卦三爻与外卦三爻的天干、地支。

| 单卦 | 内卦（初、二、三） | 外卦（四、五、上） |
|---|---|---|
| 乾 | 甲子、甲寅、甲辰 | 壬午、壬申、壬戌 |
| 兑 | 丁巳、丁卯、丁丑 | 丁亥、丁酉、丁未 |
| 离 | 己卯、己丑、己亥 | 己酉、己未、己巳 |
| 震 | 庚子、庚寅、庚辰 | 庚午、庚申、庚戌 |
| 巽 | 辛丑、辛亥、辛酉 | 辛未、辛巳、辛卯 |
| 坎 | 戊寅、戊辰、戊午 | 戊申、戊戌、戊子 |
| 艮 | 丙辰、丙午、丙申 | 丙戌、丙子、丙寅 |
| 坤 | 乙未、乙巳、乙卯 | 癸丑、癸亥、癸酉 |

- 完整 8 卦 × 内外 × 3 爻表已于 2026-09-13 由 S-001 与 S-002 逐格比对一致，并编码于 `NajiaEngine`；传统文献页码仍待领域复核。

该表当前仅支持 `EXPERIMENTAL` 实现；在传统来源和专家案例复核前不得升级为 `VERIFIED`。

## 5. 六亲（R-LIUQIN-001）

以本宫五行为“我”，按爻支五行与“我”的生克关系计算：

| 关系 | 六亲 |
|---|---|
| 同我 | 兄弟 |
| 生我 | 父母 |
| 我生 | 子孙 |
| 克我 | 官鬼 |
| 我克 | 妻财 |

不得根据问题类型或 AI 解释改写六亲。

变爻六亲仍以**本卦所属宫五行**为“我”，不得改用变卦所属宫。核心 API 将该参数命名为 `referencePalaceElement`，组装层必须沿用这一语义。

## 6. 六神（R-LIUSHEN-001）

六神从初爻起逐爻向上，固定循环：

```text
青龙 → 朱雀 → 勾陈 → 螣蛇 → 白虎 → 玄武
```

按日干确定初爻起神：

| 日干 | 初爻六神 |
|---|---|
| 甲、乙 | 青龙 |
| 丙、丁 | 朱雀 |
| 戊 | 勾陈 |
| 己 | 螣蛇 |
| 庚、辛 | 白虎 |
| 壬、癸 | 玄武 |

候选基线来自 S-001；必须通过十日干共 60 个爻位的穷举测试，并用 S-002 定位差异。

## 7. 历法约定（R-CALENDAR-001）

```kotlin
data class CalendarConvention(
    val zoneId: ZoneId,
    val dayBoundary: DayBoundary,
    val monthBoundary: MonthBoundary,
    val dayGanZhiSect: Int
)
```

当前决定：

| 项目 | 草案值 | 状态 |
|---|---|---|
| 默认时区 | `Asia/Shanghai` | 已确认；设置页可选任意 IANA 时区 |
| 用户能否修改起卦时区 | 可以；开始起卦时锁定并保存 | 已确认 |
| 月建边界 | 节交接精确时刻 | 实验口径已确认 |
| 节气数据源 | S-003 固定版本 | 实验口径已确认 |
| 节气时间基准 | lunar-java 无时区钟表值一律按固定 `UTC+08:00` 转为 `Instant`，不采用 IANA 历史 offset | 已确认 |
| 换日点 | 用户所选时区当地 00:00 | 已确认 |
| 晚子时归属 | 23:00–23:59 仍属当天 | 已确认 |
| 日柱 API | `getDayInGanZhiExact2` | 已确认 |
| 夏令时 | 使用 `ZoneRules` 解析，保存实际 offset | 候选，待测试 |

`CalendarProviderAdapter` 必须显式传入上述约定。禁止直接读取 `ZoneId.systemDefault()` 后丢弃时区信息。

月建与日柱使用两条独立时间路径：月建先把同一 `Instant` 转为 UTC+8 钟表值后调用 `getMonthInGanZhiExact()`；日柱按用户 `ZoneId` 的当地钟表值调用 `getDayInGanZhiExact2()`。禁止把纽约、伦敦等任意当地钟表值直接喂给月建 API。

## 8. 月建、日辰与旬空

- 月建取所选精确月柱的地支；具体“节”边界由 `MonthBoundary` 决定。
- 日辰取所选日柱口径的地支，同时保留完整日干支供六神和旬空使用。
- 旬空由完整日干支经独立 `XunkongEngine` 计算，每个六十甲子结果必须恰有两个地支。
- 六旬固定为：甲子旬戌亥、甲戌旬申酉、甲申旬午未、甲午旬辰巳、甲辰旬寅卯、甲寅旬子丑；以独立 60 甲子字面量表验证，不调用 S-003 生成预期。

## 9. 输出与版本

专业盘快照必须包含：

- `rulesetId`、`rulesetVersion`、`verificationStatus`。
- 原始六爻、起卦 `Instant`、`ZoneId`、实际 UTC offset、历法口径。
- 本卦八宫、卦类、世应、每爻纳甲/五行/六亲/六神、月建、日辰、旬空。
- 变卦仅保存身份及实际变爻的变后纳甲、五行和以本卦宫五行为基准的六亲；不得保存对称的第二张完整专业盘。
- 第三方历法适配器名称与版本。

实现分层必须保持：时间无关的 `StaticProfessionalChart` 与最终 `ProfessionalChartResult` 分离；日柱、月建、旬空等输入未就绪时，不得以大量 nullable 字段伪造“不完整专业盘”。

规则升级不得重算历史。任何含 `TBD` 字段的结果只能是 `NOT_AVAILABLE` 或开发测试夹具；公开 Beta 必须由产品负责人明确批准。

## 10. 升级条件

从 `0.2.0-draft` 升级为正式规格前：

- 所有规则均关联来源编号与测试 ID。
- 产品负责人批准公开 Beta 范围。

升级为 `VERIFIED` 还必须满足 `TESTPLAN.md` 的专家黄金案例门禁。
