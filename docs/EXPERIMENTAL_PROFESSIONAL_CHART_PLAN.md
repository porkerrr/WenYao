# 实验性专业排盘实施方案

> 状态：可进入规则研究与实验实现；正式专业发布仍待领域专家验收
>
> 规则集标识：`wenyao-mainstream-experimental`
>
> 初始版本：`0.1.0`
>
> 制定日期：2026-09-13

## 1. 决策

问爻不再把“缺少已签署规则集”视为全部专业排盘研发的停工条件，而是拆成两道门：

1. **实验实现门**：公开规则来源、许可证、版本、公式和争议项完成登记后，可以实现并展示明确标注的 `EXPERIMENTAL` 专业排盘。
2. **正式发布门**：只有规则集经领域顾问批准、20–50 个完整黄金案例全部通过且无未解释差分时，才可升级为 `VERIFIED`。

基础 MVP 保持现状；专业排盘作为后续增量，不阻塞基础起卦、历史和 AI 解释的交付。

## 2. 事实、推理与风险

### 2.1 已确认事实

- 当前应用已经具备三硬币起卦、本卦、动爻、变卦、历史和 AI 解释。
- 专业字段需要确定性计算；AI 只解释结构化盘面，不参与补算或纠错。
- 开源实现一致只能用于发现实现偏差，不能证明某一术数口径是唯一真值。
- GitHub 对许可证的自动识别依赖仓库内可识别的许可证文件；README 自称某许可证不等同于完成许可证审查。

### 2.2 对共享回答的采用判断

- 采用“自研 Kotlin 专业引擎 + 独立历法适配器 + 多参考差分”的架构方向。
- 采用“规则级穷举测试优先，完整经典案例作为集成黄金测试”的验证策略。
- 采用 `EXPERIMENTAL` 与 `VERIFIED` 严格分离的产品表达。
- 不直接采信共享回答中的仓库许可证、API 名、测试数量和正确性声明；这些内容必须在锁定 commit 后重新核验。

### 2.3 关键风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 参考仓库后续变更 | 规则或许可证漂移 | 固定 commit SHA，保存许可证副本与 SHA-256 |
| 多实现共享同一错误 | 差分一致但规则仍错 | 追溯传统规则来源并保留专家验收门 |
| 历法口径不一致 | 节气、子时附近结果不同 | 固定 `ZoneId`、换日口径、节气边界和历法库版本 |
| 无许可证项目被误用 | 产生版权与分发风险 | 只作人工研究或黑盒输出对照，不复制代码、表格、测试数据 |
| 实验结果误导用户 | 用户当成已验证专业结果 | UI、数据库、导出和 API 都携带验证状态与规则版本 |
| 历史随算法升级改变 | 无法复盘旧结果 | 保存完整专业盘快照，禁止按新规则静默重算 |

| `ID-VerNe/liuyao-paipan` | 测试设计研究候选 | LICENSE 文件及数据来源授权 | 无明确许可时禁止复制任何代码、表格和案例数据 |

每个获准来源写入 `docs/ruleset/SOURCE_REGISTRY.md`，至少记录 URL、commit、访问日期、许可证 SPDX、版权声明、使用方式、许可证文件哈希和复核人。

## 4. 先文档、后代码的交付顺序

第一批交付不是九个计算模块，而是下面三份可审计文档：

1. `docs/ruleset/RULESET.md`
   - 写清八宫、世应、纳甲、五行、六亲、六神、月建、日辰、旬空的公式、表格、来源与示例。
   - 所有时区、节气、换日、晚子时和流派决定必须显式记录。
   - 未决定内容统一为 `TBD`；含 `TBD` 的字段不得进入正式计算路径。
2. `docs/ruleset/TESTPLAN.md`
   - 定义穷举测试、属性测试、边界测试、差分报告和黄金案例格式。
   - 每个规则条目必须能追溯到至少一个测试 ID。
3. `docs/ruleset/SOURCE_REGISTRY.md`
   - 完成第三方来源、许可证、版本和使用边界登记。

三份文档评审通过后，才开始 Kotlin 实现。

## 5. 目标架构

```text
ThreeCoinCaster
      ↓
BasicHexagramEngine
      ↓
BasicHexagram
      ↓
ProfessionalChartEngine
      ├─ PalaceEngine
      ├─ ShiYingEngine
      ├─ NajiaEngine
      ├─ WuxingEngine
      ├─ LiuqinEngine
      ├─ LiushenEngine
      └─ CalendarEngine
             ↓
       CalendarProviderAdapter
      ↓
ProfessionalChartSnapshot
      ├─ rulesetId
      ├─ rulesetVersion
      ├─ verificationStatus
      ├─ calculatedAt
      └─ zoneId
```

技术约束：

- 所有模块为纯函数或可注入接口，UI 不包含排盘规则。
- `CalendarEngine` 输入必须是 `Instant + ZoneId + CalendarConvention`，不能读取隐式设备默认值。
- 第三方历法库必须包在适配器后，业务模型不暴露其类型。
- 参考引擎和差分工具只存在于测试/开发环境，不打入生产 APK。
- AI 请求只接收已经生成的盘面快照，不能返回覆盖专业字段的新值。

## 6. 分阶段开发计划

### P0：来源与口径冻结（2–4 人日）

- 核验四个候选仓库及许可证，固定可用 commit。
- 产出 `SOURCE_REGISTRY.md`、`RULESET.md` 0.1 草案和 `TESTPLAN.md`。
- 决定默认时区、节气月、换日点、晚子时和日柱口径。

退出条件：九类专业字段均有来源或 `TBD`，所有引用可追溯，许可证无未决项。

### P1：接口、状态和持久化（2–4 人日）

- 新增 `ProfessionalChartEngine` 与模块接口。
- Room 保存规则集 ID、版本、验证状态、时区和完整快照，并增加 migration test。
- 正式构建默认 `NOT_AVAILABLE`；内部开关允许 `EXPERIMENTAL`。
- 结果页显示“实验性专业排盘，尚未完成领域专家最终校验”。

退出条件：未验证状态无法被任何自动路径升级为 `VERIFIED`。

### P2：静态排盘规则（5–8 人日）

- 依次实现八宫、世应、纳甲、五行、六亲和六神。
- 每实现一项，同时完成对应穷举测试和规则追溯 ID。
- Kotlin 实现依据 `RULESET.md` 独立编写，不逐行翻译参考仓库。

退出条件：静态规则测试全通过，代码覆盖全部 64 卦。

### P3：历法集成（3–6 人日）

- 通过 `CalendarProviderAdapter` 集成经核验的历法库。
- 输出月建、日辰、日干、日支与旬空。
- 覆盖节气交接前后、23:00/00:00、闰年、跨时区和夏令时案例。

退出条件：边界测试全部通过，任何口径差异均有规则决议记录。

### P4：差分与黄金案例（4–8 人日，专家周期另计）

- 建立 WenYao、参考 A、参考 B 的逐字段差分工具。
- 差分只标记 `CONSENSUS`、`EXPECTED_DIVERGENCE`、`UNEXPLAINED_DIVERGENCE`，禁止多数投票修改预期答案。
- 根据可合法使用的传统来源独立整理 20–50 个完整案例，再由领域顾问复核。

退出条件：`UNEXPLAINED_DIVERGENCE = 0`，黄金案例 100% 通过。

### P5：正式发布（2–3 人日）

- 顾问签署规则集及黄金案例。
- 人工批准新规则版本从 `EXPERIMENTAL` 升为 `VERIFIED`。
- 完成两个 Android API 级别的关键流程、无障碍、迁移、离线和恢复验收。

## 7. 最低测试矩阵

| 规则 | 最低覆盖 | 核心断言 |
|---|---:|---|
| 八宫与世应 | 64 卦 | 宫、卦序类型、世位、应位 |
| 基础纳甲表 | 8 卦 × 内外 × 3 爻 = 48 | 干支、阴阳顺逆 |
| 完整纳甲 | 64 × 6 = 384 爻 | 每爻干支与五行 |
| 六神 | 10 日干 × 6 爻 = 60 | 初爻起法与顺序 |
| 旬空 | 60 甲子 | 每旬两个空亡支 |
| 六亲 | 5 宫五行 × 5 爻五行 = 25 | 生克关系映射 |
| 历法边界 | 每个节气前/中/后 | 月柱、日柱、旬空口径 |
| 完整黄金案例 | 20–50 | 九类字段逐项一致 |

此外保留属性测试：世应相隔三爻、每卦恰有一个世和一个应、六神顺序循环稳定、同一输入与规则版本输出确定、历史快照不可变。

## 8. 发布门禁

### `EXPERIMENTAL` 准入

```text
SOURCE_REGISTRY 无许可证未决项
AND RULESET 目标字段无隐式决定
AND 规则级穷举测试全部通过
AND Android 单测、Lint、Debug 构建通过
AND UI 明确显示实验性状态
```

### `VERIFIED` 准入

```text
RULESET.md 已由产品负责人和领域顾问批准
AND 专家黄金案例 >= 20
AND 黄金案例 100% 通过
AND UNEXPLAINED_DIVERGENCE = 0
AND Release 构建和两个 Android API 级别验收通过
AND 人工变更审批完成
```

任何 GitHub 项目自报的测试数量、多个引擎一致或自动化覆盖率，都不能替代上述 `VERIFIED` 准入条件。

## 9. 里程碑与总成本

| 里程碑 | 预计工程量 | 可交付结果 |
|---|---:|---|
| M1：规则与测试规格 | 2–4 人日 | 可审计的三份规则文档 |
| M2：实验性静态专业盘 | 7–12 人日 | 八宫至六神，内部可用 |
| M3：完整实验性专业盘 | 3–6 人日 | 加入月建、日辰、旬空 |
| M4：验证与正式发布 | 6–11 人日 + 专家周期 | 差分报告、黄金案例、`VERIFIED` 发布 |

总工程量约 18–33 人日，不含领域专家排期、采购和法务复核。若目标是尽快验证市场，应继续发布基础 MVP，并让专业排盘沿本方案独立推进。

## 10. 立即执行清单

1. 建立 `docs/ruleset/` 三份文档骨架。
2. 对三个拟采用来源执行 commit、许可证和 API 复核。
3. 召开一次规则口径评审，关闭时区、节气月、换日和晚子时四项决定。
4. 完成 P1 接口与持久化后，再进入九项规则实现。
5. 在任何专家验收完成前，生产界面保持 `NOT_AVAILABLE`；若产品负责人批准公开 Beta，才允许展示 `EXPERIMENTAL`。
